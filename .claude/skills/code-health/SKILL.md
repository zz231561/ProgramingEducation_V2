# 專案健檢工作流

**設計前提**：檔案大小的成本是 **AI 的檢索粒度與 token**，不是人類認知負荷。
判準因此是「檔名能不能預測內容」與「能不能一次讀完」，**不是**可維護性理論。
所以一律用**原始行數**（宣告、prompt 字串、JSX 標籤同樣佔 token，不折算）。

**不做即時攔截**：健檢在「一個邏輯變更完成後」跑，不在每次 Edit 後跑——
寫到一半暫時超標是正常的，即時擋會逼出為了過門檻的病態拆分。

---

## 階段 0 — 蒐集事實

**只執行、只讀數字，不准開始評論。** 看到第一個超標檔案就跳進解決模式會漏掉後面的。

```bash
python3 scripts/doc_selfcheck.py
npx --yes jscpd@latest backend/services backend/api web/components web/lib web/hooks \
  --min-lines 5 --min-tokens 30 --reporters console --format "python,typescript,tsx"
```

jscpd 門檻是實測校準的：預設值抓不到本專案真實的 7 行 near-duplicate。

## 階段 1 — 分流（純規則，不必讀程式碼）

| 情況 | 動作 |
|------|------|
| 檔頭有 `code-health: allow-large` 標記 | **跳過**，不再評估 |
| > 400 行 | 進階段 2，**結論不得為「不處理」** |
| 250–400 行 | 進階段 2，三選一皆可 |
| jscpd 命中且跨 **≥3 檔** | 進階段 2 |
| jscpd 命中但只跨 2 檔 | **不處理**（三行重複優於過早抽象） |
| < 250 行 | 不看 |

最後兩列是硬性的：沒有它們會忍不住「順手改善」旁邊的程式碼，違反精準修改原則。

## 階段 2 — 逐案判斷（核心）

**必須實際打開檔案讀過**，不准只看行數下結論。每個檔案回答三題：

**Q1｜檔名能不能預測內容？**
> 假設不知道裡面有什麼，只看檔名，能不能判斷「我要找的東西在不在裡面」？

不能 → **必拆信號，與行數無關**（`helpers.ts` 裝五種不相干的東西就是此類）。

**Q2｜這個檔案有幾個「變更理由」？**
> 列出「哪些需求變化會迫使我改這個檔案」。列得出 2 個以上互不相干的答案 → 拆。

**Q3｜拆了之後，一次典型修改要開幾個檔？**
> 模擬下一次最可能的改動。**≥3 檔 → 判定拆錯，放棄這個拆法。**

Q3 有**否決權**：Q1／Q2 都說該拆，但 Q3 算出 3 檔，結論仍是不拆。
病態拆分比檔案過大更難救，寧可漏拆。

**輸出格式**（強制寫全，不准省略推理）：

```
### <path>（<n> 行）
- Q1 檔名可預測性：可／不可 — <理由>
- Q2 變更理由：① … ② …
- Q3 拆分後修改跨度：<n> 檔
→ 結論：拆分／豁免／記債
→ 理由：<一句話>
```

## 階段 3 — 執行拆分（僅結論為「拆分」時）

照**變更軸**切，不照行數切。硬性禁止：

- ✗ 產生 `utils.*` / `helpers.*` / `common.*` / `misc.*` / `xxx-part2.*`——違反 Q1，製造新問題
- ✗ 為了讓兩邊都低於門檻而在中間硬切
- ✗ 外移「只被一處呼叫且不獨立可測」的函式——違反「單次使用的邏輯不抽象」
- ✗ 順手改動拆分範圍以外的程式碼

新檔命名必須通過 Q1。驗證不通過就 `git checkout` 退回，不留半成品：

```bash
cd backend && .venv/bin/python -m pytest -q
cd web && npm test && npx tsc --noEmit && npm run lint && npm run build
```

## 階段 4 — 豁免與收尾

結論為「豁免」時，在**檔案最前面 5 行內**寫（`doc_selfcheck.py` 只掃前 5 行）：

```python
# code-health: allow-large — <具體理由>
```

理由**必須能對應到 Q1–Q3 其中一題**，不接受「這樣比較好」「拆了沒意義」。

收尾（專案「文檔同步」守則）：重跑 `doc_selfcheck.py` 確認清單縮短 → 同步
`docs/roadmap.md`（打勾＋一行）、`docs/tech-debt.md`；
有設計取捨（如豁免判斷的依據）才寫 `docs/decisions.md`。

## 階段 5 — 註解語意稽核（僅 Roadmap／使用者明確要求時）

逐檔閱讀 production code，不能只靠 regex 批次刪除。刪除：① 重述下一行程式的註解；
② 已失效的 phase／日期／任務編號快照；③ 只重複函式或區塊名稱的 separator。

保留：設計理由與否決方案、安全／相容性／效能限制、非直覺 workaround、public API docstring、
外部契約、仍可執行且有明確完成條件的 TODO。註解若描述錯誤，依「當場修小問題」直接修正。

輸出以「刪除類型 → 代表例子 → 為何不影響理解」彙整，不逐檔流水帳。若只改註解，驗證至少跑
formatter／lint、type check／compile 與受影響側完整測試，確保沒有誤刪 pragma 或工具指令。

## 邊界

- 函式層級的複雜度（McCabe / 巢狀 / 參數數）走 lint 常態執行，**不在本 skill 範圍**——
  那是「每次都該過」，不是「健檢時才看」。
- 本 skill 不改動程式行為。發現的 bug 一律另案處理，不夾帶在拆分的 diff 裡。
